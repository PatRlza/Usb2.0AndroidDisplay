# ДопЭкран — проект «второй экран по USB»

> Это главный файл проекта: цель, архитектура, **память проекта** (что проверено и что решено),
> план этапов и идеи по оптимизации. Обновляется после каждого этапа.
> Последнее обновление: 2026-11-12

---

## 1. Цель

Приложение для двух Android-устройств (ТВ и планшет/телефон), которое выводит картинку игры
с планшета на ТВ **по USB-кабелю** с минимальной задержкой, как настоящий второй экран:

- формат 16:9 под ТВ без чёрных рамок (экран планшета 16:10/21:9 не мешает);
- выбор разрешения (HD / FHD / 2K) и частоты кадров;
- физический экран планшета можно выключить;
- выбор игры/приложения из списка, запуск его на «втором экране»;
- управление геймпадом;
- максимально лёгкое приложение на ТВ (слабый процессор);
- (позже) режим производительности: остановка лишних фоновых процессов.

Почему не просто кабель USB-C → HDMI: Xiaomi Pad 5 имеет USB 2.0 без видеовыхода (DisplayPort Alt Mode
нет). Сырой HDMI-сигнал по USB 2.0 не пролезает, поэтому видео **сжимается** (H.264) и передаётся потоком.

### Наблюдения ⚠️

- Тест на ТВ выполнен с **POCO F3**, а не с Pad 5. Логика та же (ADB-интерфейс у Android стандартный),
  но на Pad 5 нужно повторить, чтобы убедиться.
- Версия USB в тестере показывается «?»: это ограничение API 30 на ТВ, не ошибка.
- В списке ТВ ещё два устройства: Bluetooth-модуль MediaTek (0E8D:7663) и флешка/диск ASMedia (174C:55AA).

- Иногда бывают подтормаживания. **Причина не выяснена**. Гипотезы: нагрузка на планшет (игра + кодирование
  одновременно), нагрев и троттлинг Snapdragon 860, слишком высокий/низкий битрейт, декодирование/вывод на ПК,
  нагрузка на ПК. Нужна диагностика (раздел 6).
- В Google Play на ТВ не нашлось утилит для просмотра USB-устройств: это нормально, Play показывает
  только приложения, рассчитанные на ТВ. Это **не** доказывает, что USB на ТВ не работает.

### Главный вопрос — решён ✅

**Даст ли ТВ обычному приложению доступ к USB-хосту и захват ADB-интерфейса?** Да (тестер, 2026-11-12).
Остаётся более тонкий риск: сам протокол ADB (авторизация по RSA-ключу, окно «Разрешить отладку с этого
устройства?» на планшете) ещё не реализован и не проверен.

### Принятые решения

1. Видео сжимается H.264 (не H.265/AV1): минимальная задержка и совместимость со слабым ТВ.
2. Планшет работает как устройство, а ТВ — как **USB-хост**: приложение на ТВ реализует ADB-клиент
   поверх USB bulk-передачи и запускает на планшете сервер (по образцу scrcpy-server).
3. Картинка рендерится на **виртуальный дисплей** нужного размера (16:9), а не зеркалится: так нет рамок и
   можно гасить физический экран.
4. Приложение на ТВ: одна Activity, один SurfaceView, без Compose и лишних библиотек.
5. **Основной источник — POCO F3** (SD 870, 8 ГБ). Pad 5 не обязателен; если всё заработает на телефоне,
   планшет подключать смысла нет.
6. Стартовый битрейт по умолчанию — около 10 Мбит/с (по результатам сравнения 10M и 30M).
7. Для планшета/телефона достаточно включённой «Отладки по USB» (без root, без Shizuku).

8. **ADB-клиент по USB пишем сами** (пакет `adb` в проекте), без сторонних библиотек. Причины: протокол
   небольшой и открытый, готовые библиотеки для Android в основном рассчитаны на TCP, а не на USB,
   часть из них давно не обновляется; свой код легче и полностью под контролем.
9. **Видеосервер на телефоне не пишем, берём готовый `scrcpy-server`** (файл версии 5.0.1 из папки scrcpy,
   Apache 2.0). Клиент на ТВ должен соответствовать версии сервера. Протокол потока v5.0.1 нужно сверить
   с исходниками перед этапом 3б.
10. **Одно приложение на все устройства** (идея пользователя): один APK, роль выбирается при запуске.
    ТВ — приёмник. Телефон/планшет — помощник настройки (проверка отладки по USB, игры, профили).
    Стримить с телефона само приложение на телефоне не требуется: сервер запускается с ТВ через ADB.
11. **Оформление: Material 3 (Material You)** на обычных Views + Material Components, не Compose: меньше
    нагрузка на слабый ТВ. Динамические цвета на Android 12+ (телефон), на ТВ с Android 11 — фиксированная
    палитра. Экран трансляции — только SurfaceView, без интерфейса поверх.

12. **Управление виртуальным экраном (идея пользователя: тачпад на телефоне).** Без ввода виртуальный экран годится только для просмотра, поэтому управление — следующий приоритет (этап 3г). Порядок:
    а) **Сначала с ТВ:** пульт/геймпад, подключённый к ТВ, двигает курсор (стик/D-pad) и нажимает кнопки; события уходят в канал управления scrcpy.
    б) **Потом тачпад на телефоне** (отдельная роль единого приложения): события касаний должны попасть с телефона на ТВ **по тому же кабелю**, через обратный туннель ADB (`reverse`): приложение на телефоне подключается к `localhost:порт`, ADB переносит данные по USB в приложение на ТВ, а оно отправляет их в канал управления. Для этого `AdbUsbConnection` должен уметь принимать потоки, открытые со стороны телефона.
    в) **Геймпад для игр:** передавать как виртуальный геймпад на телефоне (в scrcpy это режим UHID), чтобы игра видела настоящий геймпад. Работает ли ввод на виртуальном экране без фокуса — проверить.
13. Приложение на виртуальном экране перед запуском останавливается (`force-stop`): иначе уже запущенное может остаться на основном экране. Для игр это значит «всегда запуск с нуля»; позже сделать настройкой.

14. **Запуск приложения на виртуальном экране — только явным компонентом** (`am start --display <id> -n пакет/активность`), активность определяется у телефона через `cmd package resolve-activity --brief`. Запуск идёт в фоновом потоке, видео читается сразу.
15. **Декодируем все кадры, показываем только самый свежий из готовых** (`VideoDecoder.outputLoop`): очередь «съедается» со скоростью декодера, а не экрана. При накоплении данных в канале (порог 300 КБ ≈ 0,25 с) пропускаем кадры до ближайшего ключевого.
16. **Перед каждым запуском и при остановке убиваем старые `scrcpy-server`** на телефоне (`pkill -f 'scrcpy[.]Server'`), в журнале пишется, сколько их было.
17. **Измерение задержки в статистике:** «Задержка канала +N мс сверх минимума» (разница времени прихода пакета на ТВ и метки кодера, минус минимум за ~20 с; абсолютную задержку так не узнать, зато видны очереди) и время декодера. Полную задержку «палец → экран ТВ» измеряем вручную: секундомер на экране + камера второго телефона.

### Запасной план (если ТВ не даст USB-хост)

Подключать планшет к недорогой Android-приставке/мини-ПК с нормальным USB-хостом, а её выход — по HDMI
на ТВ. Или рассмотреть режим по Wi-Fi 5 ГГц как запасной (задержка хуже).

## 4. Архитектура (целевая)

```
Планшет (источник)                         ТВ (приёмник)
┌─────────────────────────┐   USB-кабель   ┌──────────────────────────┐
│ server (запуск через adb)│ ─────────────► │ приложение-приёмник      │
│  • VirtualDisplay 16:9   │  H.264 + звук  │  • USB host + ADB-клиент │
│  • MediaCodec encoder    │                │  • MediaCodec decoder    │
│  • запуск выбранной игры │ ◄───────────── │  • SurfaceView (вывод)   │
│  • приём ввода (геймпад) │   управление   │  • выбор игры, настройки │
└─────────────────────────┘                └──────────────────────────┘
```

Компоненты:

1. **Сервер на телефоне.** Готовый `scrcpy-server` (открытый код, Apache 2.0, github.com/Genymobile/scrcpy):
   создаёт VirtualDisplay, кодирует в H.264, отдаёт поток. Загружается на телефон и запускается от имени
   shell через ADB; поток забираем через ADB-сервис `localabstract:` (без сети).
2. **ADB-клиент по USB на ТВ.** Собственная реализация (пакет `adb`): рукопожатие CNXN, авторизация RSA
   (AUTH), потоки OPEN/WRTE/OKAY/CLSE поверх USB bulk. Первая версия написана в этапе 3а.
3. **Приёмник на ТВ.** Читает поток, отдаёт `MediaCodec` напрямую в `Surface`, без копирования и обработки.
4. **Список приложений.** Через ADB (`pm list packages`, как `scrcpy --list-apps`), выбор пользователем,
   запуск на виртуальном дисплее (`--start-app=<пакет>` в терминах scrcpy).
5. **Профили игр.** Для каждой игры свои разрешение, fps и битрейт.

## 6. Оптимизация и диагностика подтормаживаний

### Диагностика (этап 1)

Сравнивать по одному параметру за раз, записывая результат в журнал ниже:

- `scrcpy --print-fps ...` — видеть реальный fps;
- битрейт: 8M / 12M / 20M / 30M;
- fps: 30 / 60;
- кодек: `--video-codec=h264` против `h265`;
- разрешение: 1280×720 / 1920×1080 / 2560×1440;
- с выключенным экраном планшета и с включённым;
- температура планшета и «просадка» после 10–15 минут игры;
- запуск без игры (только Telegram) — есть ли подтормаживания.

### Идеи оптимизации

**ТВ**
- Игровой режим / ALLM включить, MEMC (сглаживание) выключить;
- Приложение: один Surface, декодер напрямую, флаг низкой задержки (`KEY_LOW_LATENCY`, Android 11+),
  приём в отдельном потоке на прямых буферах;
- Закрывать фоновые приложения перед стартом (на ТВ доступно ограниченно: `killBackgroundProcesses`).

**Планшет (кодирование)**
- H.264, без B-кадров, короткий GOP, режим постоянного битрейта, низкая задержка кодера;
- выключенный физический экран (уже работает), меньше нагрузки на GPU/дисплей;
- не транслировать лишнее: звук включать только если нужен.

**Режим производительности (идея пользователя)**
Через ADB-права (shell) на планшете: остановить лишние приложения (`am force-stop`), отключить фоновые
синхронизации. Что именно допустимо и безопасно на HyperOS/MIUI — **проверить на устройстве**,
не обещать заранее. Желательно делать откатываемым и только по явному выбору пользователя.

### 6.1. Автонастройка (идея пользователя, 2026-11-12)

**Идея.** При первом запуске игры приложение само тестирует связку на 30–60 секунд, подбирает параметры и
сохраняет профиль игры. Пользователь может выбрать «Автонастройка» или «Вручную». В интерфейсе показывается
ожидаемый fps и что на него влияет.

**Ключевое наблюдение.** Поток не может быть быстрее самой игры: fps потока ≈ min(fps игры, возможности кодера).
Поэтому при замерах нужно отдельно измерять fps игры и fps потока, иначе низкий результат можно ошибочно
списать на битрейт.

**Метрики теста (что реально можно измерять):**
- fps, с которым кадры приходят на ТВ и выводятся;
- пропущенные/опоздавшие кадры и разброс времени между кадрами (дрожание);
- задержка «кодер → экран» (по меткам времени в потоке);
- температура телефона (через ADB, `dumpsys battery`) — **способ проверить на устройстве**;
- fps самой игры на виртуальном дисплее — **способ проверить на устройстве** (`dumpsys gfxinfo` / SurfaceFlinger).

**Алгоритм (черновик):**
1. Пользователю предлагается быть в обычном игровом процессе и вращать камеру (в меню тест даёт неверные данные).
2. Лестница битрейта, например 6 → 8 → 10 → 14 → 20 Мбит/с, по ~8–10 секунд на ступень.
3. Выбирается самая высокая ступень, где fps потока не упал, пропусков меньше ~1% и задержка стабильна;
   затем берётся запас около 15%.
4. Если fps игры сам по себе ниже цели (как Genshin: 40–60), предложить снизить разрешение или лимит fps.
5. Профиль сохраняется для игры; кнопка «Перетестировать».
6. Позже: **адаптивный режим** — менять битрейт на лету по загрузке (сцены в играх разные), и
   перепроверка после 10–15 минут из-за нагрева телефона.

**Что от чего зависит (для подсказки в интерфейсе):**

| Параметр | Что даёт | Цена |
|---|---|---|
| Выше битрейт | чётче картинка при движении и вращении камеры | больше нагрузка на кодер/декодер, выше риск подтормаживаний |
| Выше разрешение | чётче картинка | выше нагрузка на GPU игры и на кодер |
| Выше fps | плавнее | нагрузка на всё; поток не быстрее самой игры |
| Тяжёлая игра (Genshin) | — | GPU занят игрой, остаётся меньше ресурсов на кодирование, нагрев |
| Лёгкая игра (Minecraft и т.п.) | можно ставить высокий битрейт | — |
| Нагрев | — | через 10–15 мин возможен троттлинг, fps падает |

**Про «примерный fps».** Точный fps до теста назвать нельзя. Реалистично: до теста показывать диапазон по
типу игры, после теста — измеренное значение для этих настроек.

### 6.2. Протокол scrcpy-server 5.0.1 (подтверждено пробой на POCO F3)

Основа: `doc/develop.md` репозитория Genymobile/scrcpy; детали для 5.0.1 подтверждены реальным потоком (2026-11-12).
Поле имени устройства — **64 байта**. `start_app` серверу передавать нельзя (см. память проекта).

- Загрузка: `/data/local/tmp/scrcpy-server.jar` (через `adb push`, у нас протокол `sync:` в `AdbSync.kt`).
- Запуск: `CLASSPATH=/data/local/tmp/scrcpy-server.jar app_process / com.genymobile.scrcpy.Server <версия> key=value ...`.
  Первая строка аргументов — версия клиента; **должна в точности совпадать с версией сервера**, иначе отказ.
- Опции: `scid` (31-битное число, hex), `tunnel_forward=true` (сервер сам слушает сокет, клиент подключается),
  `audio`, `control`, `video_bit_rate`, `max_fps`, `new_display=1920x1080`, `start_app=<пакет>`, `log_level`.
- Сокет: `localabstract:scrcpy_<scid>`; до трёх подключений по порядку: видео, звук, управление.
  Если звук и управление выключены, подключается только видео. На первом сокете сервер шлёт пробный байт.
- Видеопоток (по документации): имя устройства (размер поля в документации не указан), идентификатор кодека
  (4 байта, `h264` = `0x68323634`), пакет сессии 12 байт (старший бит 1, ширина, высота),
  затем кадры: заголовок 12 байт (8 байт: флаги + метка времени PTS в 61 бите; 4 байта: размер) + данные.
  Флаги: бит 0 — пакет сессии, бит 1 — конфигурация (SPS/PPS), бит 2 — ключевой кадр.
- Формат сообщений управления — см. раздел 6.3.
- Числа в потоке — big-endian.

### 6.3. Канал управления scrcpy-server 5.0.1 (по исходникам scrcpy: control_msg.c/h)

Второе подключение к `localabstract:scrcpy_<scid>` (после видео, при `control=true`). Все числа big-endian, первый байт — тип.

| Тип | Сообщение | Поля | Байт |
|---|---|---|---|
| 0 | INJECT_KEYCODE | action u8, keycode u32, repeat u32, meta u32 | 14 |
| 2 | INJECT_TOUCH_EVENT | action u8, pointer_id u64, x u32, y u32, w u16, h u16, pressure u16 (0xFFFF = 1.0), action_button u32, buttons u32 | 32 |
| 3 | INJECT_SCROLL_EVENT | x u32, y u32, w u16, h u16, hscroll i16, vscroll i16 (значение/16 в фикс. точке), buttons u32 | 21 |
| 10 | SET_DISPLAY_POWER | on u8 | 2 |
| 17 | RESET_VIDEO | — | 1 |
| 12–14 | UHID_CREATE/INPUT/DESTROY | виртуальный HID (возможный путь для настоящего геймпада) | — |

`w`, `h` — текущий размер видео (из пакета сессии); сервер сам пересчитывает координаты. Устаревшие MOVE сбрасываются, если очередь > 4.
Схема управления v0.7: пульт — стрелки двигают курсор (ускоряются при удержании), OK = тап, долгий OK = «взять и тащить» (следующий OK отпускает), Назад = Назад на телефоне, долгий Назад = выход, Меню = показать/скрыть статистику.
Геймпад: левый стик/крестовина — курсор, A (удержание) = палец прижат, правый стик = прокрутка, B = Назад, Y = Домой, Start = статистика, Select = выход.
Экран телефона в режиме виртуального дисплея гасится по умолчанию и включается при выходе.

### 6.4. Исследование задержки (2026-11-14)

Путь кадра: приложение на телефоне → виртуальный дисплей (такт основного экрана) → аппаратный кодер → scrcpy-server → ADB/USB →
ТВ: чтение → декодер → вывод на Surface → обработка картинки самим ТВ → панель.
Что известно:
- Декодер ТВ (OMX.MS.AVC.Decoder) держит кадр в среднем ≈ 13 мс (строка «Декодер» в статистике) — меньше одного кадра, значит
  заметной буферизации/переупорядочивания в нём нет; патч SPS (bitstream_restriction, max_dec_frame_buffering=1) пока не нужен.
  У Moonlight он включён только для Nvidia/Qualcomm/Broadcom; в errata указано, что на некоторых MediaTek-декодерах он наоборот добавляет задержку.
- Ключи низкой задержки декодера у Moonlight: `low-latency`=1 (Android 11), `vdec-lowlatency`=1 (MediaTek, Amlogic), `vendor.low-latency.enable`
  (Amlogic), `vendor.qti-ext-dec-low-latency.enable`, `vendor.rtc-ext-dec-low-latency.enable` (Exynos), `KEY_OPERATING_RATE`, `KEY_PRIORITY`=0.
  Все они выставляются в v0.14 (с повтором без них, если декодер не принял).
- Android 11+: `Window.setPreferMinimalPostProcessing(true)` просит экран включить ALLM/игровой режим, если он есть
  (проверка: `Display.isMinimalPostProcessingSupported()`). Включено в v0.14, результат пишется в журнал.
- Кодер телефона: `latency=0, priority=0, max-bframes=0`, расширение Qualcomm `vendor.qti-ext-enc-low-latency.enable=1`; в режиме «Минимум» ещё CBR (`bitrate-mode=2`).
- Частота обновления телефона 120 Гц (ключи AOSP `min_refresh_rate/peak_refresh_rate`, включаются вместе с режимом производительности; на MIUI могут игнорироваться).
- Измерение: «Отклик на касание» (касание курсором → первый кадр, пришедший после него, показан декодером). Мерить на статичном экране
  (список чатов Telegram), где кодер молчит до изменения картинки; в играх с постоянной анимацией цифра занижена.
- Остаётся вне нашего контроля: обработка картинки в самом ТВ (игровой режим, выключить сглаживание движения), вертикальная синхронизация (≈ 8 мс в среднем).
- Идеи на потом: патч SPS как переключатель-эксперимент; Baseline-профиль кодера (`profile=1`); свой форк scrcpy-server (SET_BITRATE на лету, меньше буферов); асинхронные USB-запросы вместо `bulkTransfer`.

## 7. Как собрать и запустить тестер (этап 0)

1. Android Studio → **Open** → выбрать папку `tester-tv`.
2. Если Studio спросит про Gradle — согласиться на предложенный вариант (wrapper/Gradle по умолчанию);
   если предложит обновить плагин Android (AGP) — можно согласиться.
3. Дождаться Gradle Sync. Если нужны SDK Platform 34 — установить, Studio предложит сама.
4. Собрать: **Build → Build Bundle(s) / APK(s) → Build APK(s)**. Файл: `app/build/outputs/apk/debug/app-debug.apk`.
5. Установить на ТВ. Варианты:
   - **Флешка:** скопировать APK, открыть на ТВ файловым менеджером (разрешить установку из неизвестных
     источников);
   - **ADB по Wi-Fi:** на ТВ включить режим разработчика и отладку по сети, затем с ПК:
     `adb connect <IP ТВ>:5555` и `adb install app-debug.apk` (папка scrcpy уже содержит `adb.exe`).
6. Запуск на ТВ: приложение «USB Тестер ТВ» (может быть в списке всех приложений).
7. Подключить планшет к ТВ через хаб. На планшете: отладка по USB включена, режим «Передача файлов».
8. В тестере нажать «Обновить», затем «Тест доступа к ADB-интерфейсу», подтвердить запрос доступа на ТВ,
   нажать тест ещё раз.
9. **Результат записать в журнал (раздел 8)** или прислать скриншот.

Как читать отчёт:
- `[1] USB host: ДА` — система заявляет поддержку;
- в списке есть устройство с `VID:PID` планшета (у Xiaomi VID обычно `2717`) и пометкой `<-- ADB`;
- `claimInterface = УСПЕХ` — всё хорошо, этап 0 пройден.

### Видео-проба (этап 3б, тестер v0.3)

1. Скопируйте файл **`scrcpy-server`** (без расширения) из папки `scrcpy-win64-v5.0.1` в
   `tester-tv/app/src/main/assets/` и пересоберите приложение.
2. Установите на ТВ, подключите POCO F3 через хаб, откройте «USB Тестер ТВ».
3. Нажмите **«Видео-проба: зеркало»**. Приложение загрузит сервер на телефон, запустит его и 6 секунд читает поток.
   Пока идёт проба, **листайте экран на самом телефоне**, чтобы шёл поток (на статичной картинке данных мало).
4. Потом **«Видео-проба: экран 16:9»**: то же, но на виртуальном экране (запустится Telegram). Картинка на нём
   статична, поэтому данных будет мало — это нормально, нас интересует формат начала потока.
5. Пришлите скриншоты: строки `[сервер]`, hex первых байт, найденный формат и скорость потока.

Возможные результаты и что они значат:
- `[сервер]` пишет про несовпадение версии → поправим `SERVER_VERSION` в `ScrcpyProbe.kt`;
- «Идентификатор кодека не найден» → формат потока отличается, разберём по hex;
- скорость близка к 10 Мбит/с в режиме «зеркало» → канал и сервер работают.

### Трансляция (этап 3в, тестер v0.4)

1. Пересоберите проект (файл `scrcpy-server` в `assets/` уже должен лежать), поставьте на ТВ.
2. Телефон подключён через хаб, USB-доступ для ТВ уже выдан (в списке устройств «Доступ выдан: да»).
3. **«▶ Трансляция: зеркало»**: на ТВ откроется картинка экрана телефона (вертикальная, с чёрными полями по бокам).
   Листайте на телефоне.
4. **«▶ Трансляция: экран 16:9»**: виртуальный экран 1920×1080, на нём запускается выбранное приложение
   (кнопка «Приложение: …» переключает Telegram / Genshin / Play Маркет / Настройки). **Управлять им пока нельзя**
   (канала управления ещё нет, этап 3г), это тест картинки и скорости.
5. Вверху слева статистика: размер видео, Мбит/с, кадров на входе и показано в секунду, среднее время декодера (мс),
   потеряно кадров. OK/Menu на пульте скрывает её, Назад — выход.
6. Пришлите фото экрана и скажите, как выглядит картинка (чёткость, подтормаживания, цвета, на весь ли экран).
7. **v0.5:** под статистикой появился «журнал» (последние 7 строк): там видно, что ответил сервер, поддерживает ли декодер размер видео, и результат запуска приложения (`[am] ...`). Для Telegram/Genshin пришлите фото журнала, если снова чёрный экран.
